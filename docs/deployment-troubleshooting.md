# Deployment and form connection troubleshooting

The deployment branch selects the GitHub environment: `dev → dev`, `qa → qa`, `main → prod`. Check **Settings → Environments → selected environment**, not only repository-level settings. Environment settings can override repository values. A failed validation/sync does not publish a new deployment; the existing website keeps its previously built configuration.

## Auth0 audience mismatch

The preference API's audience is the exact **Identifier** of your custom Auth0 API (Applications → APIs), including any trailing slash. It is not the SPA client ID and is not the Auth0 Management API identifier.

Set the GitHub environment **Variable `NEXT_PUBLIC_AUTH0_AUDIENCE`** to that Identifier. CI now uses this single value both for browser token requests and server `AUTH0_AUDIENCE`, eliminating drift from the older duplicate Secret. The old GitHub `AUTH0_AUDIENCE` Secret is unused and can be removed. In an ignored local environment file, both names still need the same exact value. Validation reports setting names and whitespace problems without printing values.

Similarly, `AUTH0_DOMAIN` (Secret) and `NEXT_PUBLIC_AUTH0_DOMAIN` (Variable) must identify the same tenant hostname. `NEXT_PUBLIC_AUTH0_CLIENT_ID` is the **SPA** application's ID; the Management ID/secret belong to a **separate M2M** application. Follow [Auth0 setup](setup.md) for callback URLs, origins, passwordless email, API scope and provider templates.

## Netlify site does not match the website URL

This message is generated by the repository's hostname guard **after a successful site lookup**. It is not a Netlify rejection of the website URL. No settings are written when the comparison fails. The guard prevents a dev/QA/prod configuration from being copied into another project.

The mechanism is Node's built-in `fetch`, not curl or the Netlify CLI. It sends a bearer-authenticated [Get a site request](https://open-api.netlify.com/#tag/site/operation/getSite):

```text
GET https://api.netlify.com/api/v1/sites/{NETLIFY_SITE_ID}
Authorization: Bearer [redacted]
```

The actual request substitutes the URL-encoded environment Secret for `{NETLIFY_SITE_ID}`. Logs retain the placeholder and never print IDs or tokens. They now show HTTP status, the selected environment, expected website hostname, whether the returned ID equals the requested ID, and hostnames from `ssl_url`, `url`, `custom_domain`, and `domain_aliases`. They also recognize the default `<project-name>.netlify.app` hostname derived from a valid returned project name, including when the API's URL fields describe the custom domain. Netlify documents this [project-name/default-URL relationship](https://docs.netlify.com/manage/projects/how-projects-work/).

Example diagnostic output with synthetic domains:

```text
Site environment: prod
Expected NEXT_PUBLIC_SITE_URL hostname: "website.example.com"
[Netlify request] GET https://api.netlify.com/api/v1/sites/{NETLIFY_SITE_ID} (IDs and body values redacted)
[Netlify response] GET https://api.netlify.com/api/v1/sites/{NETLIFY_SITE_ID} -> HTTP 200
Returned site.id equals NETLIFY_SITE_ID: true (ID values redacted)
Returned custom_domain hostname: "other.example.com"
Returned default domain from site.name hostname: "fixture-project.netlify.app"
Hostname comparison: MISMATCH; DNS and redirects are not used for this check
```

To fix the mismatch:

1. In Netlify, open the project that actually owns the intended website domain. Copy its **Project ID** from project settings, not a team/account ID, deploy ID, URL, or another project's ID.
2. In **GitHub → Settings → Environments**, open the environment selected by the branch (`main` uses **prod**). Set Secret `NETLIFY_SITE_ID` to that Project ID and confirm `NETLIFY_AUTH_TOKEN` can access it. Environment-level settings may override repository-level settings.
3. Set Variable `NEXT_PUBLIC_SITE_URL` to the intended plain HTTPS origin. Use the canonical custom domain for production. Paste URL text only, without surrounding quotes, Markdown, commas or an API path. With and without a trailing `/` compare identically. Do not switch URLs merely to conceal a project-ID mismatch.
4. Compare the next run's returned hostnames with the expected hostname. A custom domain must be assigned to **that selected project**, not only configured in DNS or on a different Netlify project. A redirect between two domains is not evidence that both belong to the same project.

For a separate read-only check, supply just `NETLIFY_AUTH_TOKEN`, `NETLIFY_SITE_ID`, and `NEXT_PUBLIC_SITE_URL` through your shell or ignored environment file:

```sh
npm run deploy:inspect
# Or load an existing ignored local file explicitly:
node --env-file=.env.local scripts/sync-netlify-env.mjs --inspect-site
```

This command performs only the site GET and comparison; it needs no Auth0/model credentials, synchronizes nothing, and creates no deployment. A mismatch exits nonzero after logging diagnostics. It prints only allowlisted public hostname fields, never the whole site response (which can contain private repository/configuration data). GitHub may still mask a hostname if you stored that same text as a Secret; do not disable masking or dump responses to work around it. Run the read-only command locally when necessary.

After the hostname guard succeeds, synchronization reads the site's environment key inventory using `GET https://api.netlify.com/api/v1/accounts/{account_slug}/env?site_id={NETLIFY_SITE_ID}`. It updates an existing key with `PUT .../accounts/{account_slug}/env/{KEY}?site_id={NETLIFY_SITE_ID}` or creates a new key with `POST .../accounts/{account_slug}/env?site_id={NETLIFY_SITE_ID}`. A concurrent deletion (PUT returns 404) can use creation; 403 never triggers an alternate write attempt. The body contains the named key, production-context value, and all-scope preset. Logs show method, route template, key name and HTTP status; team slugs, account/site IDs, authorization and body values remain redacted. The inventory response is read privately to retain key names only; values are never logged or written to a local file.

## Site GET succeeds but environment access returns 403

The site API and environment-variable service use different account-locator conventions. Although the OpenAPI path parameter is named `account_id`, Netlify's own [pinned CLI env:set implementation](https://github.com/netlify/cli/blob/v27.16.2/src/commands/env/env-set.ts) passes **`site.account_slug`** for environment reads/writes. The sync now follows that behavior instead of passing the opaque `site.account_id` returned by the site lookup. The slug is obtained automatically from the checked site; no extra GitHub setting is needed. If it is missing, sync stops rather than guessing another account identifier.

The CLI's [all-scope preset](https://github.com/netlify/cli/blob/v27.16.2/src/utils/env/index.ts) is `builds`, `functions`, `runtime`, **`post_processing`**. Its source explicitly notes the spelling difference from OpenAPI's `post-processing`. The sync now uses the CLI-compatible underscore spelling and lists existing keys before choosing update versus creation. It does not request granular Functions-only scope, paid Secrets Controller, or `is_secret`.

The earlier UUID account route and scope spelling were integration mistakes; the site GET's 200 did not validate either of those write-request parameters. After this correction, leave the matching site URL/Project ID in place. Push the corrected script and start a run using that commit. A successful site inspection alone is read-only and does not prove environment write access. If a 403 persists with the corrected account-slug route and scope preset, the remaining cause needs investigation of the token's authorization for that team/site (including any SSO restrictions), plan capabilities, or Netlify support. The status alone cannot identify which policy denied it. Do not publish the token or full environment response while investigating.

## What the pipeline verifies

Build and publish run in one adapter lifecycle:

```sh
npx netlify deploy --build --prod --context production --message "$GITHUB_SHA" --json
```

`--context production` selects build-time configuration and is valid with `--build`. `--prod` selects the chosen project's live deployment. The Next.js adapter prepares CDN assets, routing, images and functions before the CLI uploads them. Netlify CLI rejects `--context` together with `--no-build`; this workflow therefore builds inside the deploy command. GitHub environment `prod`, server `SITE_ENVIRONMENT=prod`, and Netlify context `production` remain as configured. See the [CLI deploy reference](https://cli.netlify.com/commands/deploy/).

### HTML works but public images return 404

The pinned Next.js adapter copies `public/` and browser chunks into `.netlify/static`, then temporarily swaps that CDN directory into the configured `.next` publish path during `onPostBuild`. Its `onEnd` restores raw Next.js output. Running a standalone `netlify build` followed by a separate `netlify deploy --no-build` loses that temporary publish handoff and can upload raw `.next`, leaving public images absent.

The workflow now keeps build and upload in one CLI invocation. `netlify.toml` still declares `publish = ".next"`, as required by the adapter; the adapter owns its temporary swap. Do not permanently change this to a raw public/static export or remove a failing image check.

The local `netlify/plugins/verify-release` plugin runs after the adapter. Its `onBuild` checks public browser configuration when runner-only `BUN2TOO_RELEASE_CHECK=true`. Its `onPostBuild` refuses raw server/build output and verifies every public file and every compiled browser asset against the prepared CDN file bytes **before upload**. Missing SVGs, logos, WebP artwork or stale chunks therefore fail before publication. A regression test exercises the pinned adapter's actual copy/swap/restore functions. Post-publication smoke checks retain the legacy SVG and additionally verify the official logo, current artwork, and referenced JavaScript/CSS responses. A failure in this post-publication step means publication already happened; it does not automatically roll back the live site.

1. Validate all required configuration and cross-setting consistency before changing Netlify.
2. Request a Management API token with the configured M2M credentials and required scopes. This creates no users, reads no customer profiles and sends no email. A failure reports HTTP status and corrective setting names; provider bodies/tokens are withheld.
3. Probe the configured public Insights index, one article when available and RSS. Only public GETs are used; a wrong origin or incompatible response blocks synchronization with safe diagnostics.
4. Confirm the selected Netlify site matches `NEXT_PUBLIC_SITE_URL`, then sync named production-context values. Logs show public hostname comparisons, redacted API route templates, HTTP status and key names. A failed sync stops publication, although earlier keys in that sync may already have been updated.
5. Run build and upload in one Netlify deploy invocation. The local validation plugin checks public Auth0/Turnstile/tracking values and all prepared CDN asset bytes before upload. A successful fixture build cannot substitute for this release build.
6. Publish, check real routes and invalid/unauthorized API inputs, then check runtime inquiry readiness (and AI readiness if enabled). Readiness means configuration/context is present, not that a valid customer transaction has completed.

Public `NEXT_PUBLIC_*` settings are frozen into browser JavaScript during a Next.js build. Updating a Netlify runtime variable cannot repair an old browser bundle. Commit/push the fix or trigger a new build on the correct branch after correcting dashboard settings. Rerunning an old workflow run uses that old commit. GitHub debug logging will still mask secret values; it cannot fix inconsistent or absent settings. Normal logs now include safe diagnostics, so enabling debug is unnecessary.

| Insights shows “Taking a short pause” | Set `INSIGHTS_API_ORIGIN` in the selected GitHub environment to the working editorial HTTPS origin, without `/insights`. Run `npm run insights:check` with private local configuration. New deployments check the actual public API before syncing; the page uses request-time rendering and smoke checks inspect article content, not HTTP status alone. | AI answer controls absent/unavailable | Complete [Open WebUI setup](support.md), including dedicated public-only access, all four Secrets and explicit enable Variable. There is no implicit connection to a host just because DNS exists. |

Rate-limit storage precedes CAPTCHA; gateway errors alone do not prove verification failed. Readiness flags are not live storage/AI health checks. See [support request limits and diagnostics](support.md#ai-data-handling-and-limits). |

The site's global CSS hides the outer branding iframe by its known ID and exact title, including late injection. Browser extension channel/back-forward-cache errors, an extension's `SERVICE WORKER NOT FOUND` log, and third-party `unload` policy warnings do not identify an Auth0 failure. Inspect the actual `/authorize` response and root callback's OAuth error, then check Auth0 tenant logs. Compare with a clean browser profile. Never paste tokens, cookies, state, full authorize URLs, or unredacted provider responses into public issues. The app displays a fixed recovery message rather than echoing provider descriptions.

## Local and live verification limits

`npm test`, `npm run docs:check`, `npm run typecheck`, isolated `npm run build:test` and `npm run test:e2e` use fixtures; they cannot prove your provider dashboard settings or customer delivery. `npm run deploy:check` validates runner environment configuration without synchronizing or contacting providers. For an ignored local file, use `node --env-file=.env.local scripts/sync-netlify-env.mjs --check`; required deploy credentials still need to exist, and no values are printed. Do not run the mutating sync against a live site just to inspect local setup.

After deployment, use an approved test identity/inquiry in dev to verify actual authentication, email verification, topic activation/withdrawal and private record persistence. Ask a public AI test question only when enabled. Do not publish tokens, raw provider errors, environment files, customer data or screenshots of credentials while debugging. See [security inventory](security.md).
