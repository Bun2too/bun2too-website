# Customer support and private inquiries

The website provides `/support` FAQs and a lazy-loaded **Contact Bun2Too** dialog. Private inquiry collection works independently of AI. Optional AI answers use a server-side Open WebUI connection; they appear only when explicitly enabled with complete configuration. Opening the dialog never sends an AI question. The launcher stays hidden on embedded signup.

Public FAQ copy is sourced from Contentful (or the committed snapshot) for the support page, FAQ schema and `/llms.txt`. This does not automatically ingest CMS content into Open WebUI knowledge; review and update that public-only collection separately. See [CMS design](contentful-design.md).

## Private inquiry setup

Configure Netlify hosting/Blobs, `SUPPORT_SESSION_SECRET` (at least 32 random characters), the Turnstile public/secret key pair, and SES delivery below. Register every deployed website hostname with the Turnstile widget. See [security](security.md) for the exact GitHub environment inventory and [deployment troubleshooting](deployment-troubleshooting.md) for connection checks.

`GET /api/support/session` initializes a signed HttpOnly visitor cookie and returns `inquiries`/`chat` availability flags, never credentials or records. **HTTP 200 means the check succeeded; it does not mean either feature is ready.** Inquiry readiness requires storage context, verification configuration and complete SES configuration. `inquiryUnavailableReasons` contains generic categories (`storage`, `verification`, `email`) for diagnosis; these are configuration checks, not successful storage/email probes. AI readiness is independent of SES. `POST /api/support/inquiries` validates origin, explicit consent, bounded fields, request ID, honeypot, CAPTCHA and distributed limits before storing a record and requesting an email notification. It returns a reference only after confirmed persistence. There is no public inbox or generic blob listing/retrieval API.

Netlify supplies storage credentials at runtime. Administrators review `inquiries/` in **Netlify → site → Data & Storage → Blobs → bun2too-support**. Records contain a reference, contact details, topic, message, consent purpose/version/time, creation/expiry timestamps, and email notification status. Email is self-reported, not proof of identity. Inquiries do not enroll marketing, attach AI questions, or create a helpdesk ticket automatically. Review the store and management inbox regularly.

### SES delivery to the management inbox

The **Send a private inquiry** entry opens the dialog; its submit button posts JSON to `/api/support/inquiries`. It never opens a mail client. The separately labeled **Email our team directly** fallback uses the visitor's mail application and does not submit the form or include its draft.

The header's **Let’s connect** button opens the same dialog directly on the current page, including when already on `/contact`. It does not require navigating to the contact page first. Opening only checks session availability; it never submits an inquiry, sends email or calls AI.

Set these server-only names in ignored `.env.local` for local work, and GitHub environment **Secrets** for deployments. Deployment sync forwards them to Netlify runtime; they are never CMS fields or browser values.

| Setting | Purpose |
| --- | --- |
| `SUPPORT_SES_SMTP_HOST` | SES SMTP hostname for the sender’s region, without scheme or path. |
| `SUPPORT_SES_SMTP_PORT` | 587/2587/25 for required STARTTLS, or 465/2465 for implicit TLS. |
| `SUPPORT_SES_SMTP_USERNAME` | Dedicated SES SMTP username. |
| `SUPPORT_SES_SMTP_PASSWORD` | Matching SES SMTP password, different from an AWS API secret. |
| `SUPPORT_INQUIRY_FROM_EMAIL` | One verified sender mailbox, without a display name. |
| `SUPPORT_INQUIRY_TO_EMAIL` | One private management inbox receiving all inquiry notifications. |

Local `SUPPORT_SENDER_SMTP_*` names are accepted as legacy aliases, but the deployment workflow and inventory use `SUPPORT_SES_SMTP_*`. Existing valid values are preserved during configuration changes. `SUPPORT_SES_ACCESS_KEY_ID`/`SUPPORT_SES_SECRET_ACCESS_KEY` are API credentials, not the SMTP settings used by this adapter. No API access key is needed here. SMTP region is selected by the configured regional hostname.

`npm run support:email:check` connects, negotiates TLS and authenticates without sending mail. It loads `.env.local` and withholds all credential/provider values. Success does not verify sender/recipient eligibility or inbox delivery. The standard `npm run dev` supplies local Netlify storage automatically; `dev:support` is a compatibility alias.

Restrict the SMTP identity’s IAM permissions to `ses:SendRawEmail` for the selected sender identity, recipient and region. The transport uses explicit SMTP authentication, mandatory TLS with certificate validation, bounded connection/socket waits, and abortable sends. Debug logging and attachment file/URL access are disabled. It never uses the Netlify host’s AWS role. Verify the sender in that SES region; while SES is sandboxed, verify the recipient too or obtain production access. An SES provider configured in Auth0 only sends Auth0's messages; it is not shared with this website. See [AWS sending requirements](https://docs.aws.amazon.com/ses/latest/dg/send-email-smtp.html).

After private persistence, the server sends two plain UTF-8 emails. The management notification contains reference, name, contact email, topic, message and consent timestamp/version, with the visitor as Reply-To. Its sender and recipient come only from server configuration. The requester acknowledgment goes only to the validated contact address in the saved record and contains the reference and generic receipt text, without reflecting the inquiry body, name or management inbox. It confirms private storage, not a response deadline. No credentials, cookies, AI questions, browser-selected management recipients, CC or BCC are sent. Consent explicitly includes storage, email to the team and a requester acknowledgment (version `2026-11-12.2`). Update the corresponding published Contentful privacy block when enabling this feature; the committed fallback includes the new processor disclosure. Netlify's 90-day cleanup does not delete mail from SES logs or recipient mailboxes; manage those separately.

The response is **201** with `notification:"accepted"` and `acknowledgment:"accepted"` when SES acknowledges both, which does not prove inbox delivery. If either email cannot be confirmed, a saved inquiry returns **202** with its reference and each independent email status; the dialog displays the corresponding warning. Separate persisted conditional claims prevent repeated submissions from sending either email twice. SMTP sends are not retried automatically. A timeout or interrupted process can leave `sending`/`unconfirmed`; operators must check SES/mailbox status before arranging any resend. A legacy saved record with no notification claim can be retried through its original signed session and request ID; do not create a new ID merely to bypass an uncertain send. There is no automatic outbox worker or delivery-event receiver.

The API has a 24-second total budget, including rate-limit storage (four seconds), CAPTCHA (eight), persistence (four), and both emails (twelve seconds combined), bounded by the remaining total. A saved reference and already-confirmed email statuses survive a later-stage timeout. Logs contain only the email channel, stage, allowlisted SMTP error code and numeric SMTP response code. No raw SES error, recipient address, message body or credentials are logged. SMTP authentication alone cannot verify sender/recipient eligibility. SES sandbox restrictions can reject an acknowledgment to an unverified visitor even when management notification succeeds; verify test recipients or request production access for the SES region.

The visitor cookie lasts 24 hours. HMAC-derived ownership/request IDs isolate retries; conditional writes make saved submissions idempotent. Pseudonymous counters enforce five inquiries per visitor/hour and twenty per Netlify connection address/hour. Raw connection addresses are not stored. Records expire after 90 days; daily cleanup at 04:00 UTC removes expired inquiries, limits, and legacy conversations. Existing records are not deleted by a source edit.

### Local development and session errors

Run `npm run support:setup` to generate a cryptographically random signing secret in the ignored, owner-readable `.env.local`. It preserves other settings and an existing valid secret, never prints the value, and refuses to replace a nonempty short secret automatically. The current development launcher automatically reloads the new file setting. The secret stays server-only; do not use a shared default or put it in `NEXT_PUBLIC_*`.

`GET /api/support/session` returns **503** when `SUPPORT_SESSION_SECRET` is missing or shorter than 32 characters, before storage, CAPTCHA or AI is checked. The server logs `Support configuration unavailable` with only the setting name and `missing`/`too-short`. An unrelated application's `token` cookie is ignored; this endpoint uses only `bun2too_support`. Nothing is connecting in the background: the visitor message says **currently unavailable**, with email/FAQ alternatives. The dialog checks availability on each open, limits the check to ten seconds, and offers a manual retry while preserving the inquiry draft. It does not retry submissions or AI questions automatically.

**Check availability again** only repeats this GET; it does not provision storage, configure SES, send a message or repair dependencies. The result explicitly says whether the form is ready or still unavailable.

The standard `npm run dev` provides [Netlify Dev's sandboxed local Blobs store](https://docs.netlify.com/build/data-and-storage/netlify-blobs/) automatically. It loads optional `.env.contentful.local` defaults, then `.env.local` overrides; existing shell variables take precedence. Inquiry and AI flags still depend on their environment configuration, not the command's name. The development launcher automatically restarts its own runtime when environment files change; inherited shell exports still take precedence and require a command restart when changed. After stopping your own existing process, run:

```sh
npm run support:setup
npm run dev
```

Open the proxy origin `http://localhost:3000`, preserving the local Auth0 origin; Netlify supplies local storage context to its child Next.js process. The command uses development-mode CAPTCHA behavior: verification is skipped only when no secret is configured outside production. Production builds require both Turnstile keys for inquiry readiness. Keep any CAPTCHA test keys confined to an isolated test environment. AI still needs its separately approved configuration; a successful session does not verify an AI response or a saved inquiry. This setup command does not configure Netlify deployment secrets.

SES settings are also required for `inquiries:true`; local Netlify storage does not provide a mail sender. Local submissions with real SES settings send real mail, so use an authorized test sender/inbox.

`dev:support` and `dev:cms` are aliases to `dev`. Direct `next dev` or local production `npm start` bypasses the local Netlify runtime and can return a 200 session with false flags and `storage` as the reason. That means the session check succeeded but its dependencies are unavailable. Do not fabricate a Blobs context or change readiness flags to bypass private storage/rate limits. Deployed Netlify builds receive their production storage context from the Next.js adapter; they do not run a development command.

The pinned local Blobs server omits GET ETags, although its listing returns conditional-write versions. In `NETLIFY_DEV=true` outside production, the storage adapter brackets a fresh read with matching listed versions, retrying a changed snapshot up to three times. This restores safe repeated rate-limit reads and email claims without invented ETags. Production continues to require GET ETags. Tests use the actual local Blobs server, temporary records and mocked email sends, including a concurrent write during the read.

Check the session without copying browser cookies:

```sh
curl --silent --show-error --max-time 15 --write-out '\nHTTP %{http_code}\n' \
  http://localhost:3000/api/support/session
```

## Connect Open WebUI

This repository implements the website adapter, not the hosted Open WebUI installation, model serving, or knowledge ingestion. No live model/knowledge ID or credential is committed. The API follows Open WebUI's [chat and knowledge collection contract](https://docs.openwebui.com/reference/api-endpoints/) and [API key controls](https://docs.openwebui.com/features/authentication-access/api-keys/).

Open WebUI has no per-key granular permissions: the key inherits its owner's permissions. Global API-key enablement and an optional instance-wide endpoint allowlist are separate controls, with UI placement depending on the installed version. A 403 alone does not prove a particular model or collection was denied. Compare the exact completion request against an unauthenticated request and a deliberately invalid key before attributing the failure to resource permissions. Never rotate a key merely to work around an endpoint policy.

`npm run support:ai:check` performs read-only checks for the configured model and collection without printing hostnames, IDs, model inventory or document content. It makes no inference request. HTTP 401 indicates rejected authentication; use a service account API key rather than an expiring browser/session JWT. HTTP 403 requires checking global API-key enablement, the non-admin account/group's API-key permission, endpoint restrictions and resource access. The website needs `/api/chat/completions`; read diagnostics additionally need `/api/models` and the specific `/api/v1/knowledge/{id}` route. A denied diagnostic GET alone does not establish that completions are denied. The runtime logs the actual completion status and a safe reason (`authorization`, `upstream`, `network`, `response`) without provider bodies. The development launcher reloads changes to `.env.local` by restarting the local runtime with fresh settings. Older, already-running launcher versions need one manual restart to pick up this behavior. A successful Postman call combined with a fast local authorization failure can indicate stale inherited startup configuration; compare a fresh adapter/runtime before changing credentials or backend permissions.

1. In the authorized Open WebUI administration interface, create a dedicated **non-admin service user/group** for website support. Restrict it to the selected public-support model and public knowledge collection. Disable access to internal knowledge, other models, workspace tools, actions, web browsing, MCP, terminals, code execution and private files. Review model defaults and inherited permissions too; request parameters alone cannot enforce isolation from a privileged model/account.
2. Create a knowledge collection containing only approved public material: service descriptions, support FAQs, public Insights, account/subscription instructions, privacy and cookie information. Let ingestion finish and confirm that only public records are searchable. Never include this repository's environment files, deployment/security inventory, internal documents or customer records. Review changes before adding documents; a prompt is not an authorization boundary.
3. Configure a dedicated support model using that approved material, grounded answers, uncertainty when information is absent, and no promises about account access, pricing or delivery commitments. Manually test retrieval in Open WebUI using the service user's permissions. Keep its actual model and collection IDs private.
4. Enable API keys for that service user, generate a separate key, and restrict allowed API endpoints to `/api/chat/completions` where your installed version supports this. Do not use an admin credential. Configure upstream rate/concurrency/token budgets too. The website never provisions or edits models, knowledge or provider accounts.
5. In each GitHub environment (`dev`, `qa`, `prod`), set Secrets `OPENWEBUI_BASE_URL` (HTTPS origin, no API suffix), `OPENWEBUI_API_KEY`, `OPENWEBUI_MODEL_ID`, and `OPENWEBUI_KNOWLEDGE_ID`. Set Variable `OPENWEBUI_PUBLIC_SUPPORT_ENABLED=true` **only after the public knowledge/access boundary is approved**. Keep it false until ready. The deployment sync forwards these to the selected site's production runtime; they never use `NEXT_PUBLIC_*`. No Open WebUI base URL is hardcoded in source.
6. Ensure Netlify Functions can reach the configured origin through your proxy/firewall. The fixed upstream route is `/api/chat/completions` using bearer authentication, the server-selected model, and `files: [{type: "collection", id: ...}]`. No browser input can choose a provider/model/collection/tool. Proxy authentication must accept this service credential; do not expose an unauthenticated model endpoint.
7. Commit/push and deploy to dev, then use an approved public test question. Check retrieval correctness, unknown-question handling, provider failures and public-only links. Verify private prompts/documents cannot be retrieved. Promote only after this live check. Setting credentials alone is not proof of retrieval quality or provider isolation.

### AI data handling and limits

The separate unchecked AI consent sends a single bounded question (up to 1,500 characters) to Open WebUI and its configured model provider. Each question is independent; prior messages, inquiry forms, login state, email addresses and browser cookies are not forwarded. The API requires same origin, a signed browser session, CAPTCHA and distributed limits (ten questions per visitor/hour, thirty per Netlify connection address/hour). It bounds output tokens, response bytes and request time. No automatic retry repeats a paid model request.

The chat handler has a 25-second total deadline, including response-body reads. Rate-limit storage has a four-second combined budget, CAPTCHA an eight-second budget, and the provider request a maximum of 20 seconds within the remaining total budget. The browser waits up to 30 seconds. Expired deadlines abort downstream fetches and return a JSON 503; they never bypass storage limits or verification. Storage SDK retry waits cannot keep the HTTP response pending indefinitely. Gateway HTML and browser/network timeouts display a recovery message, retain the question, and do not automatically resubmit it. These bounds provide a controlled failure response; they do not repair an unreachable storage or AI service.

For a pending chat request, inspect the deployed Next.js function logs for `Public support chat stage` and `Public support chat failed`. Entries contain only a stage (`validation`, `rate-limit-storage`, `captcha`, or `ai-provider`), elapsed milliseconds, and the failure status. No question, owner/IP identifier, cookie, token, private host/model/collection, or provider response is logged. Storage runs before CAPTCHA; a failure at `rate-limit-storage` means CAPTCHA and the model were not called. A normal rejected CAPTCHA returns JSON 400. A Cloudflare gateway error page alone does not establish a CAPTCHA failure. Session readiness flags confirm configuration/context only, not a successful storage operation or AI response. Check Netlify Blobs runtime access for storage failures; check Turnstile keys/hostname/action for verification failures; check backend connectivity, proxy authentication, service-user permissions and provider latency for `ai-provider` failures. See [Cloudflare's gateway troubleshooting](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-5xx-errors/error-502-504/).

The website does not persist question/answer transcripts or attach them to inquiries. The latest answer exists in browser component memory. Rate counters and the visitor cookie remain; closing/reloading the page clears the answer. **Closing the dialog alone does not clear component memory.** Open WebUI, model providers and infrastructure may still retain API/security logs: set and verify their retention/logging policy independently, disable prompt-content logging where supported, and do not promise zero retention without validating it. Use no sensitive visitor data in questions.

Only plain answer text is returned. Raw documents, provider citation objects, model/collection/session IDs, reasoning fields, errors, and credentials are not forwarded. URLs in answer text are limited to public Bun2Too/Insights pages; unknown/private links are omitted, and returned HTML is rendered as text. These filters reduce accidental exposure; public-only service-account/model/knowledge permissions are the primary boundary. AI output is informational and cannot change an account, subscribe a visitor or submit an inquiry. Human escalation remains a separate consented form.

## Verification and retirement

Unit/browser tests use isolated fixtures for credentials, provider responses and storage. They cover origin/consent/input checks, fixed model/knowledge selection, withheld provider errors, inquiry ownership/idempotency, failures without false receipts, cookie controls and absence of AI calls before opt-in. They do not establish live retrieval, account callback configuration, persisted Netlify records, or email delivery.

After an authorized dev deployment, submit one approved test inquiry and verify its reference privately in Netlify, check the retention function, complete a test Auth0 login and newsletter confirmation, and ask one approved public AI question if enabled. CI smoke checks only invalid/unauthorized inputs and readiness flags; they never create a subscriber, save an inquiry or call a model.

The earlier provider is removed from the integration. Remove its obsolete secrets/settings from GitHub and Netlify, revoke retired credentials, and handle old provider records under your retention policy. Editing this repository does not change remote dashboards or installations. Keep the signing secret, storage and CAPTCHA settings for inquiries regardless of AI enablement.
